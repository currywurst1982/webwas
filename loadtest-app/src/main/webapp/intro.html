성능테스트 개론

← 시나리오 대시보드로
요청하신 참고 글(ssseung.tistory.com/557)은 작성 환경에서 열리지 않았고 검색 결과에도 나오지 않아 내용을 확인하지 못했습니다. 아래는 원문을 직접 확인한 공개 자료(Grafana k6 공식 문서, nGrinder 소스·위키)와 앞서 인용했던 자료를 근거로 정리했습니다. 출처를 못 찾은 주장은 넣지 않았습니다.

1. 성능테스트로 답하려는 질문

기능테스트가 "제대로 동작하나?"를 묻는다면, 성능테스트는 "많은 사람이 동시에 써도 빠르고 안정적인가?"를 묻습니다. 실무에서는 보통 다음 질문에 답하려고 합니다.

한 서버당 TPS는 얼마나 나오며 목표 TPS를 달성하기 위해서 필요한 서버 구성은 무엇인가? — 네이버파이낸셜 기술블로그 「nGrinder를 활용한 부하테스트」 (검색 결과 발췌)
Many things can go wrong when a system is under load. The system must run numerous operations simultaneously and respond to different requests from a variable number of users. — Grafana k6 문서 「Load test types」 (부하가 걸리면 많은 것이 잘못될 수 있다. 시스템은 수많은 작업을 동시에 처리하고, 수가 변하는 사용자들의 다양한 요청에 응답해야 한다)

2. 테스트 종류와 이 대시보드의 대응

테스트 이름은 자료마다 다릅니다. k6 문서도 "no consensus even exists about the names of these test types"(이름에 대한 합의조차 없다)라고 씁니다. 아래 표의 단위·통합은 소프트웨어 공학의 단위/통합테스트(코드 수준)를 이 대시보드의 맥락(요청 단위 점검 / 전체 연결 점검)에 맞게 옮긴 것입니다.

종류무엇을 확인하나 (k6 문서 원문)부하 · 시간이 대시보드에서
단위테스트요청 하나하나가 맞게 동작하는지 (주소, 입력칸 이름, 응답코드, 성공 글자, 토큰)1건씩④-1 단위테스트 (WAS가 직접, 몇 초)
통합테스트 ≈ 스모크"validate that your script works and that the system performs adequately under minimal load" (스크립트가 동작하고 최소 부하에서 시스템이 적절히 동작하는지 확인)낮음 · 짧게④-2 통합테스트 (에이전트에서 1명 × 몇 회)
부하테스트"assess how your system performs under expected normal conditions" (예상되는 평소 조건에서 어떻게 동작하는지 평가)평소 수준 · 5~60분④-3 성능테스트 + 합격 기준
내구성(Soak)테스트"assess the reliability and performance of your system over extended periods" (장시간 동안의 안정성과 성능 평가). 원문은 장시간 사용 뒤에만 나타나는 문제로 "response time degradation, memory or other resource leaks"(응답시간 저하, 메모리 등 자원 누수)를 듭니다평소 수준 · 수 시간④-3 성능테스트의 "내구성테스트(60분)" 빠른 설정 + 모니터 화면의 메모리 그래프
스트레스테스트"assess how a system performs at its limits when load exceeds the expected average" (부하가 평균을 넘을 때 한계에서 어떻게 동작하는지)평균 이상 · 5~60분④-3 성능테스트에서 Vuser를 평소보다 크게
임계테스트 (Breakpoint)"gradually increase load to identify the capacity limits of the system" (부하를 점점 늘려 시스템의 용량 한계를 찾음). 원문: "it's also known as capacity, point load, and limit testing"깨질 때까지 증가④-4 임계테스트 (자동 단계 증가 + 자동 멈춤)
스파이크테스트"validate the behavior and survival of your system in cases of sudden, short, and massive increases in activity" (갑작스럽고 짧은 폭증에서의 동작)매우 높음 · 몇 분지원 안 함 (nGrinder에서 순간 폭증 패턴을 만들려면 스크립트 수정이 필요)

표의 영어 원문 출처: Grafana k6 문서 「Load test types」 (github.com/grafana/k6-docs, testing-guides/test-types)

3. 진행 순서

Start with smoke tests, then progress to higher loads and longer durations. — k6 「Load test types」 (스모크테스트로 시작해 더 큰 부하, 더 긴 시간으로 나아가라)
Run breakpoints only when the system is known to perform under all other test types. — k6 「Breakpoint testing」 (임계테스트는 다른 모든 테스트에서 정상 동작이 확인된 뒤에만 하라)
  1. 단위테스트: 입력값이 맞는지 먼저 확인 (주소·입력칸 이름·계정 오류를 몇 초 만에 발견)
  2. 통합테스트: 실제 에이전트에서 대상 서버까지 연결·스크립트가 동작하는지 확인 (연결 시간 초과 같은 문제가 여기서 드러남)
  3. 성능테스트: 예상 부하로 합격 기준을 통과하는지 확인 → 필요하면 같은 부하로 장시간(내구성)
  4. 임계테스트: 어디까지 버티는지(용량 한계) 확인

서버를 새로 띄운 직후에는 결과가 불안정할 수 있습니다.

초기 서버의 불안정한 상태가 테스트 결과에 영향을 미치지 않도록 부하테스트 시작 전 1~5분 동안 서버 웜업을 진행합니다. — 네이버파이낸셜 기술블로그 (검색 결과 발췌)
Stick to simple load patterns. … Avoid "rollercoaster" series where load increases and decreases multiple times. — k6 「Load test types」 (단순한 부하 패턴을 쓰고, 부하가 여러 번 오르내리는 '롤러코스터'는 피하라)

4. 핵심 지표 (nGrinder 기준)

지표뜻근거
TPS초당 처리한 테스트(요청) 건수. 높을수록 좋음"TPS: 평균 TPS (초당 처리량이므로 높을 수록 좋다.)" — binghe819 nGrinder 완벽가이드
Peak TPS테스트 중 가장 높았던 TPS"Peak TPS: 최고 TPS" — 같은 문서
평균 응답시간 (MTT)요청 1건의 평균 처리 시간"Mean Test Time: 평균 테스트시간 (평균 Response Time = Latency)" — 같은 문서
에러율에러 ÷ (성공 + 에러) × 100이 대시보드의 계산식
Vuser (가상 사용자)동시에 요청을 보내는 가상 사용자 수. nGrinder에서는 에이전트당 프로세스 × 스레드"The number of virtual users in each agent, which is multiplied by process count and thread count." — nGrinder 위키 Test Configuration

nGrinder 기본 통계에는 p95 같은 백분위 응답시간이 없습니다. 평균만 보면 일부 느린 요청이 가려질 수 있으니, 필요하면 대상 서버의 APM(예: Pinpoint)을 함께 보세요.

5. 공식: TPS · 응답시간 · 동시 사용자

성능테스트 입문 자료들에서 다음 관계식을 씁니다 (검색 결과로 확인, 자료마다 용어 정의가 조금씩 다름).

TPS = 액티브 사용자 수 ÷ 평균 응답시간(초)
TPS = 동시 사용자 수 ÷ (평균 응답시간 + Think Time)

Think Time은 사용자가 화면을 읽거나 입력하느라 다음 요청 전에 쉬는 시간입니다. 이 대시보드의 스크립트는 쉬는 시간 없이 계속 요청하므로(Think Time = 0) 첫 번째 식이 그대로 맞아야 합니다.

실제 측정값으로 검산 (이 대시보드 검증 때 nGrinder로 측정)

시나리오Vuser평균 응답시간공식 예상 TPS (Vuser ÷ 응답시간)실제 TPS
단순 조회421.46 ms4 ÷ 0.02146 ≈ 186187.0
토큰 로그인 API421.03 ms4 ÷ 0.02103 ≈ 190189.5
CSRF 로그인431.68 ms4 ÷ 0.03168 ≈ 126126.9

활용법: 결과의 TPS가 이 식과 크게 다르면 측정이 이상하다는 신호입니다(에이전트 과부하, 에러로 빨리 끝나는 요청 등). 거꾸로 목표를 세울 때도 씁니다. 예: 목표 TPS 500, 응답시간 0.2초를 유지해야 한다면 쉬는 시간 없는 가상 사용자 약 500 × 0.2 = 100명이 필요합니다.

6. 결과 해석: 포화와 임계점

Vuser를 늘리면 처음에는 TPS가 같이 늘다가, 어느 순간부터 TPS는 그대로이고 응답시간만 늘어납니다(포화). 더 늘리면 TPS가 오히려 떨어지기도 합니다.

고부하 영역에서 일정 User 수를 초과하면 Buckle zone으로 진입해서 처리량이 줄어드는 현상이 발생한다 — 「내가써본 nGrinder」 SpringCamp 2015 발표 (검색 결과 발췌)
This test commonly has to be stopped manually or automatically as thresholds start to fail. When these problems appear, the system has reached its limits. — k6 「Breakpoint testing」 (기준이 깨지기 시작하면 수동·자동으로 멈춘다. 그 문제가 나타나면 시스템이 한계에 도달한 것이다)

이 대시보드의 임계테스트는 다음 중 하나가 나오면 멈추고, 직전 단계를 임계점(감당 가능한 최대 부하)으로 보고합니다.

  • 평균 응답시간이 기준(ms)을 넘음
  • 에러율이 기준(%)을 넘음
  • Vuser를 늘렸는데 TPS 증가가 5% 미만 (포화) — 5%는 이 대시보드가 정한 경험적 기준이며 업계 표준이 아닙니다
  • 테스트가 오류로 중지됨

7. 결과를 믿을 수 있게 하려면

  • 에이전트와 대상 서버를 분리: "가능한 Controller와 Agent 그리고 테스트 서버 모두 각각 서로 다른 물리적 서버에서 구축해줘야한다." — binghe819 nGrinder 완벽가이드. 같은 서버에 두면 에이전트가 쓰는 CPU 때문에 결과가 실제보다 나빠집니다.
  • 같은 조건에서 반복: 같은 스크립트·같은 환경에서 Vuser만 바꿔 비교해야 의미가 있습니다 (모니터 화면의 포화점 그래프는 같은 테스트 이름끼리 묶음).
  • 운영 서버·운영 계정 금지: 허락받은 테스트 서버와 테스트용 계정만 쓰세요.
  • 한 번의 테스트로 모든 위험을 볼 수는 없음: "no single test type eliminates all risk." — k6 「Load test types」
